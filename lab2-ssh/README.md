#  SSH로 서버에 접속하면 발생하는일
제일 처음 서버에 접속하게되면 전체적인 Flow는 다음과 같다.

1. TCP 연결 수립 (Port 22)
2. SSH 프로토콜 버전 교환 (SSH-2.0...)
3. 클라이언트와 서버가 **키교환(Key Exchange, 보통 Diffie–Hellman 계열)**을 통해 서로 협력하여 공통의 비밀(shared secret) 을 안전하게 도출(derive)하고, 그 결과로 **대칭 세션키**들을 만들어 사용
4. 서버 호스트키 제공(ssh-keyscan 명령으로 해쉬값을 볼수있다) → 클라이언트가 known_hosts 와 대조(지문 확인)
5. (클라이언트는) 3단계에서 생성된 세션키(ession id)를 자신의 Private로 서명해서 서버로 보낸다.
6. 사용자 인증: publickey 방식 — 서버는 등록된 클라이언트의 Public키(@~/.ssh/authorized_keys)로 클라이언트가 서명한 세션키를 **검증(만)** 한다. 이 검증이 성공하면 서버는 **“아, 이 사람은 분명히 개인키를 가지고 있구나”** 라고 판단 → 인증 완료. 그래서 결국 본인 인증 = 내 PC 안에 있는 개인키 소유 증명 이라고 이해하면 된다.
7. 서버가 서명 검증 성공하면 로그인 허용(세션이 열린다)되고, 이후 모든 데이터는 앞서 만든 **대칭 세션키**로 암호화되어 주고받는다.


**예:**
```shell
  ssh root@15.134.34.54
```
위와같이 접속하면, 클라이언트는 서버의 호스트키(host key) 신뢰 여부를 확인하는 단계를 거친다. 
- SSH 서버(예: 리눅스 서버)는 자신을 식별하기 위한 고유한 공개키(host public key)를 가지고 있다.
- 클라이언트(당신의 PC)가 처음 접속할 때, 서버는 이 공개키를 제시하고, 클라이언트는 이를 기반으로 암호화된 통신을 시작하게된다.

만일 아래와 같은 메시지가 나타난다면.
```shell
    The authenticity of host '15.134.34.54 (15.134.34.54)' can't be established.
    ED25519 key fingerprint is SHA256:**********************************.
    This host key is known by the following other names/addresses:
    ~/.ssh/known_hosts:10: 54.206.102.99
    
    Are you sure you want to continue connecting (yes/no/[fingerprint])?
```
이것은 당신의 클라이언트(ssh)가 이 서버의 호스트키를 이전에 본 적이 없다는 뜻이다. 그래도 접속할것인지 묻는것이고 따라서 "y"를 선택하면
명시적으로 이 접속을 신뢰한다고하면서 접속을 시도하게된다. 그리고 이 서버의 호스트키가 당신의 ~/.ssh/known_hosts 등록된다.

이**서버의 지문**은 아래의 명령어로 서버의 로그인없이도 확인이 가능하다.
```shell
    # ssh-keyscan으로 공개키를 받아서 ssh-keygen으로 지문 출력 (bash에서 동작)
    ssh-keyscan -t ed25519 15.134.34.54 2>/dev/null | ssh-keygen -lf -
      256 SHA256:********************************** 15.134.34.54 (ED25519)
```

#  ~/.ssh/authorized_keys @Server

~/.ssh/authorized_keys 파일은 서버 측에서 "누가 접속을 허용되는가"를 정의하는 목록이다.

### 역할
- **클라이언트(접속자)의 공개키를 저장하는 곳이다.**
- ***SSH 접속 시 클라이언트가 자신의 개인키(private key)로 서명하고, 서버는 authorized_keys 안에 있는 공개키(public key) 로 검증한다.**
- 검증이 성공하면 비밀번호 없이 접속이 허용된다 (public key authentication).

### 역동작 과정
- 서버는 로그인하려는 사용자의 홈 디렉토리에서 ~/.ssh/authorized_keys 파일을 확인한다.
- 이 파일 안에 있는 공개키들 중 하나가 클라이언트가 제시한 개인키에 대응되는지 확인한다.
- 일치하면 인증 성공 → 로그인 허용.
- (이때 서버는 절대 개인키를 갖고 있지 않다(않아야한다). 개인키는 클라이언트 PC에만 있어야 한다.)


### 특징
- 파일은 서버 사용자 계정별로 존재다.
  - 예: ubuntu 사용자라면 /home/ubuntu/.ssh/authorized_keys
- 한 사용자 계정에 여러 개의 공개키를 추가할 수 있어, 여러 개발자/운영자가 같은 계정으로 접속할 수 있다.
- 각 줄이 공개키 한 개에 해당한다. (보통 ssh-rsa AAAAB3... user@host 형식)

# 단계별 상세 설명
#### 1) TCP 연결 수립
    - 클라이언트(당신의 PC) → 서버 15.134.34.54:22 로 TCP 3-way handshake (SYN/SYN-ACK/ACK).
    - 연결 성공하면 SSH 레이어로 넘어간다.

#### 2) SSH 프로토콜 및 서비스 식별 교환
    - 서버와 클라이언트가 텍스트로 프로토콜 버전 교환: 예 SSH-2.0-OpenSSH_8.9 등.
    - 이후 바이너리 메시지 교환으로 전환된다.

#### 3) 키 교환 (KEX, 예: Diffie-Hellman)
    - 이 단계에서 서버/클라이언트는 서로 암호 알고리즘(예: kex 알고리즘, 대칭암호, MAC)을 협상한다.
    - Diffie-Hellman 등으로 공유 비밀(세션 키) 을 만들고, 이를 바탕으로 대칭 암호화 키와 세션 식별자(session id) 를 생성한다.
    - 세션 식별자(session id) 는 이후 publickey 인증 과정에서 서명할 데이터의 일부로 사용된다(중요!).

#### 4) 서버 호스트키 제공 및 검증 (host key)
    - 서버는 자신의 호스트 공개키(예: ed25519, rsa)를 클라이언트에게 보낸다.
    - 클라이언트는 로컬 ~/.ssh/known_hosts 에 저장된 항목과 비교:
        - 일치하면 계속 진행.
        - 불일치하면 SSH가 경고: “The authenticity of host '...' can't be established.” — 이때 지문(fingerprint)을 확인해야 한다.
    - (안전) 지문을 수동으로 확인하려면 서버 측에서 호스트 공개키의 지문을 확인:
        - 예: ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub (서버에서 실행)
    - known_hosts에 여러 IP/이름으로 다른 키가 등록돼 있으면, 호스트키 충돌 경고가 뜬다(예: 로드밸런서/IP 재할당 등).

#### 5) 암호화된 세션(대칭키) 설정
    - KEX 결과로 얻은 키로 모든 이후 트래픽(인증 포함)을 암호화한다.

#### 6) 사용자 인증 — publickey 방식의 내부 동작
    - 클라이언트가 공개키를 제시(offer)
        - 클라이언트는 서버에 “내가 이 공개키(어떤 key-type, 어떤 공개키)로 인증하고 싶다” 라고 알린다.
        - 서버는 해당 공개키가 ~root/.ssh/authorized_keys(또는 사용자 홈의 해당 파일)에 있는지 체크한다.
    - 서버가 허용 신호(OK) 응답
        - 공개키가 authorized_keys에 있으면 서버는 SSH_MSG_USERAUTH_PK_OK 같은 응답으로 "이 키로 인증 시도해도 된다" 를 보낸다.
    - 클라이언트가 서명 전송
        - 클라이언트는 세션 식별자(session id) + 사용자 인증 요청 데이터(사용자명, 서비스 이름 등)를 묶어 개인키로 서명한다.
        - 이 서명(=증명)을 서버로 보낸다 (SSH_MSG_USERAUTH_REQUEST 내 포함).
    - 서버가 서명 검증
        - 서버는 authorized_keys 에 저장된 공개키로 서명을 검증한다.
        - 검증 성공 → 로그인 허용. 실패 → 인증 실패.
    - 핵심: 서버는 절대 사용자의 개인키를 보거나 전송받지 않는다. 오직 클라이언트가 개인키로 만든 서명만 받고 공개키로 검증한다.

#### 7) 인증 성공 → 세션 접속
    - 서버는 인증 성공을 알리고, 쉘/명령 실행 세션을 열어준다.
    - 이후 데이터(터미널 입력/출력)는 세션 키로 암호화되어 교환된다.

# 비밀번호 로그인 vs. 개인키

#### 1. 비밀번호
- 장점: 간단함
- 단점: 비밀번호 유출 위험, 자동화/스크립트에 불편
```
    [클라이언트] --------------------> [서버]
       접속 요청 (ssh user@server)
    
    [서버] ------------------------> [클라이언트]
    서버 공개키 전송 (호스트 키 확인)
    
    [클라이언트] --------------------> [서버]
    사용자 이름(user) 전달
    
    [서버] ------------------------> [클라이언트]
    "비밀번호 입력해라" 요청
    
    [클라이언트] --------------------> [서버]
    비밀번호 입력 (암호화되어 전송)
    
    [서버]
    비밀번호 검증 → 성공 시 세션 시작
```

#### 2. 개인키 기반 로그인 방식
- 장점: 비밀번호 없이도 안전, 자동화에 적합 (예: 배포 파이프라인, Ansible)
- 단점: 개인키 분실 시 위험 → 반드시 chmod 600 ~/.ssh/id_rsa 같은 권한 관리 필요
```
    [클라이언트] --------------------> [서버]
       접속 요청 (ssh user@server)
    
    [서버] ------------------------> [클라이언트]
       서버 공개키 전송 (호스트 키 확인)
    
    [클라이언트 <-----> 서버]
       키 교환 (Diffie-Hellman/ECDH) → 세션키 생성
    
    [서버] ------------------------> [클라이언트]
       난수 challenge 생성 → "너 진짜 user 맞아?" 질문
    
    [클라이언트]
       개인키(id_rsa)로 challenge 서명
    
    [클라이언트] --------------------> [서버]
       서명(signature) 전송
    
    [서버]
       authorized_keys에 등록된 공개키로 서명 검증
       → 성공 시 로그인 완료
```

#### 3. 두 방식 공통점
- 항상 세션키(대칭키)로 암호화된 통신을 함 → 기밀성 유지
- 서버는 호스트 키로 자신을 증명, 클라이언트는 비밀번호 또는 개인키로 사용자 인증

**그러니까 비밀번호 로그인은 서버가 비번을 직접 확인하는 방식이고,  개인키 로그인은 서버가 challenge를 내고 클라이언트가 개인키로 서명해서 본인임을 증명하는 방식이다.**
